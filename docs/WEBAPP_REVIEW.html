Failure review · mosaic design webapp

The app is not being killed. It is throwing.

The crash on holylogin06 is an unhandled widget exception, not FASRC's arbiter. A saved pipeline stores num_designs: 500; the form that draws it caps the field at 200; Streamlit raises; and because all six tabs render on every rerun with no error boundary, one out-of-range integer blanks the entire page. Two other problems are real but separate — the launcher does not survive an SSH disconnect, and the login node holds you to a hard 8 GiB / 1-core budget shared across everything you run there.

Confirmed cause Reproducible from data on disk

At 12:39:00 and again at 12:40:39 the app logged StreamlitValueAboveMaxError: The value 500 is greater than the max_value 200, raised from ui_helpers.py:63 by way of the Pipeline tab's generate form. The process had been up and healthy since 08:48. There is no OOM message, no signal, no truncated log — the server kept running and served an exception page instead of the UI.

The 500 is not a typo. It is what the DIO3 campaign actually ran: pipelines/dio3_2way_500b/gen_boltzgen/node.json and its Proteina sibling both record num_designs: 500. Opening Inspect a past pipeline → Load into editor pulls those params into a form whose catalog caps the field at 200. Because the loaded pipeline lives in st.session_state["pipeline"], every subsequent rerun re-raises: the app is stuck until the browser session is reset.

01 The crash path, exactly

  1. The data. A pipeline node persists whatever it was submitted with. pipeline.submit() writes node.json verbatim — there is no schema check on the way out, and none on the way back in.
  2. The reload. Pipeline.from_run_dir() reconstructs the DAG from those shards and hands the raw params dict straight to the editor (pipeline.py:112).
  3. The mismatch. _generate_form calls params_block(…, dict(node.params)), which passes the stored 500 as value= while reading max_value= from design_config.GENERATIVE_MODELS["boltzgen"]["params"]["num_designs"]["max"] == 200.
  4. The throw. Streamlit validates min ≤ value ≤ max and raises. Nothing between ui_helpers.widget() and app.py catches it. → the exception escapes to the script runner, so the page renders a traceback instead of any tab 
webapp/ui_helpers.py:57-67

def widget(key, name, spec, current):
    t = spec["type"]
    if t == "int":
        return st.number_input(label,
                               min_value=spec.get("min", 0),
                               max_value=spec.get("max", 10000),   # 200
                               value=int(current …),             # 500  ← raises
                               step=1, key=key, help=help_)

Note the asymmetry that makes this a design flaw rather than bad luck: the bounds come from the catalog, but the value comes from user data that the catalog never governed. Any code path that can write a param — a submitted run, an uploaded DAG JSON, an edited config — can produce a value the form refuses to draw.

02 Every failure mode found

1

Out-of-range persisted parameter takes down the whole app

Confirmed

Covered above. The same shape exists in three more places that have not fired yet but will: the optimize node caps soft steps at 300 while the Launch tab lets you set 500 (OPTIMIZER_PARAMS["n_steps"]["max"]), so importing a Launch config with 400 soft steps crashes identically; the hallucinate node caps num_designs at 64; and _screen_form calls ["boltz2","boltz1","af2","of3","protenix"].index(node.params["model"]), which raises a bare ValueError for any model string outside that list.

2

No error boundary, and all six tabs execute on every rerun

Confirmed Amplifier

st.tabs is client-side only — the tab strip is CSS, but every with tab: block runs server-side on every single rerun. So the Pipeline tab's exception blanks Launch, Generate, Monitor, Results and Docs too, even though the user was never looking at Pipeline. It also means each keystroke pays for all six tabs: the target list, the SLURM queries, the file scans, the whole Launch form.

This is the single highest-leverage thing to change. It converts "one bad number bricks the app" into "one tab shows an error", and cuts per-interaction work by roughly 6×.

webapp/app.py:126-145
3

connect.sh runs the app in the SSH foreground — it dies on disconnect

Confirmed

connect.sh tells you "Ctrl+C disconnects; the app keeps running on the cluster." It does not. The script runs ssh -t … "streamlit run …" with the server in the foreground of a TTY session, so Ctrl+C delivers SIGINT straight to Streamlit and a dropped connection delivers SIGHUP. There is no nohup, no setsid, and no & anywhere in the repo. Close the laptop, lose the app. docs/WEBAPP.md:22 repeats the same false claim.

This is very likely what "crashes when launched on the login node" feels like in normal use — the app vanishes with nothing in the log, which is exactly the symptom singularity/webapp.sbatch:8-12 already warns about and attributes to the arbiter.

webapp/connect.sh:22, 25-43 · docs/WEBAPP.md:22

Environmental

03 How the app is put together

The layout is deliberate and worth keeping: pure modules hold the logic and know nothing about Streamlit, tab modules hold only UI, and app.py is bootstrap plus dispatch. Nothing in the app imports mosaic or runs a model — it reads files and queues SLURM jobs. 2,931 lines total.

What one click actually costs

Streamlit re-executes the whole script on every widget interaction. Because the tabs are client-side, that means all of the following happens each time you type a character into any field:

  1. Session registry read from ~/.mosaic_webapp/sessions.json, five working subdirectories mkdir -p'd.
  2. store.list_targets() globs targets/ and reads every FASTA and every .a3m to count unique rows — memoized on (path, mtime, size), so this part is already cheap after the first pass.
  3. All six tab bodies execute top to bottom.→ Launch alone builds ~60 widgets across 10 sections
  4. Eight subprocess.run calls to sacctmgr, sinfo, squeue, sacct.→ ~0.5–0.8 s, uncached, every time
  5. store.list_campaigns() and list_screens() scan designs/ and pipelines/*/* — memoized on directory mtimes.
  6. If the Pipeline tab holds a loaded DAG, every node's form is rebuilt from its stored params.→ where the crash occurs

The caching work in the last two commits was the right instinct and is genuinely effective — store._CACHE keys on (mtime, size) for files and on directory mtime for listings, so a 1 MB MSA is read once rather than on every keystroke. What it does not address is that six tabs run when one is visible.

The batch route already exists and its header comment already explains exactly why it should be preferred. It costs one extra SSH hop (ssh -J through the login node, printed for you in the job's output) and gives you dedicated cores instead of a contended slice. The gap is purely that connect.sh and docs/WEBAPP.md still point at the login node — and that the job's 8-hour walltime silently ends the session, which is worth stating in the docs rather than discovering.

05 What to change, in order

Tier 0 — stop the crash

~30 lines. Fixes the reported problem outright.
Clamp instead of raise, in one place
3 lines
ui_helpers.py

In widget(), clamp current into [min, max] before passing it to number_input, and emit an st.caption when it was clamped so the user is told rather than silently corrected. This single change kills the confirmed crash and two of the three latent ones.

Give every tab an error boundary
6 lines
app.py

Wrap each tab_module.render(...) in try / except Exception and show st.exception(e) inside that tab. A broken tab then costs you that tab, not the app. Do this even after the clamp — it is the difference between a bug and an outage.

Make the catalog caps match what you actually run
1 line
design_config.py

num_designs is capped at 200 but the DIO3 run used 500 — the cap is simply wrong. Raise it, and derive the Pipeline tab's hard-coded step limits (300 / 200 / 64) from OPTIMIZER_PARAMS instead of restating them, so the two can never drift again.

Guard the .index() lookups
2 sites
pipeline_tab.py

_screen_form and the generator selectbox both call list.index() on a stored string. Fall back to index 0 when the value is not in the list, the way resource_picker already does.

Tier 1 — make it stay up

Config and docs only. No app code.
Switch the documented launch route to the batch job
docs +
connect.sh

Point docs/WEBAPP.md and connect.sh at sbatch singularity/webapp.sbatch. If you want to keep a login-node fallback, it must be setsid nohup … & with a pidfile — the current script's promise that it survives Ctrl+C is false and should be deleted either way.

Bound the two unbounded caches
~10 lines
store.py, viewer.py

Cap store._CACHE and viewer._HTML_CACHE — an LRU of a few dozen entries is plenty. 3Dmol HTML blobs are megabytes each and currently accumulate for the life of the process, against a budget you share with every other thing you run on that node.

Tier 2 — make it cheap

This is where the simplification you asked about lives.
Render one tab, not six
~15 lines
app.py

Replace st.tabs with a sidebar st.radio and dispatch to a single render function. Roughly 6× less work per interaction, all six SLURM-querying tabs stop querying when you are not on them, and the blast radius of any future exception shrinks to the visible tab. Highest payoff per line in this document.

Cache the cluster queries
2 decorators
cluster.py

accounts() and partitions() change on the order of weeks. Wrap them in st.cache_data(ttl=3600) at the call site (keeping cluster.py Streamlit-free), or memoize with a timestamp inside the module. Removes six subprocess spawns per rerun.

Consider dropping pandas
judgment call

36% of a 65-second cold start, for three charts and some tables. Altair accepts a list of dicts via alt.Data(values=…), and st.dataframe will render a list of dicts directly. Worth measuring before committing — but if restarts are frequent while you iterate, this is the biggest single win available.

Simplify the Pipeline tab's forms
structural

It is the newest and largest UI surface, it re-implements the Generate and Launch forms with slightly different bounds, and it is the only tab that has crashed. The narrower version — build DAGs by uploading or composing JSON, and keep the rich forms in Generate and Launch where they already exist — would delete most of the duplicated bounds along with the class of bug they cause. Worth deciding on before adding more node types.
